Для получения аудиопотока с микрофона используют navigator.mediaDevices.getUserMedia({audio: true}), затем создают MediaStreamAudioSourceNode из возвращённого потока и подключают его к аудиоконтексту. Рекомендуется указать в конструкторе AudioContext параметр latencyHint: "interactive" (или числовое значение в секундах) для минимизации задержки. Опции AudioContextOptions также допускают указание sampleRate (по умолчанию используется частота аудиоустройства). После запуска контекста реальная задержка (AudioContext.baseLatency) зависит от платформы и может проверяться программно. Важно, что узел MediaStreamAudioSourceNode **может автоматически буферизовать вход** (в зависимости от реализации), добавляя непредсказуемую задержку. Поэтому на практике полезно экспериментировать с разными настройками буфера (например, указывать latencyHint, подбирая sampleRate, renderSizeHint) и измерять audioCtx.baseLatency.

Для низколатентной обработки аудио используется **AudioWorklet** — скрипт в отдельном аудиопотоке. Это современная замена устаревшего ScriptProcessorNode. AudioWorklet выполняется стабильно, обрабатывая фиксированное число сэмплов (обычно 128) за вызов функции process(). **Преимущество** AudioWorklet в том, что он не добавляет скрытых буферов внутри себя — каждый вызов возвращает результат для точно тех же 128 сэмплов, что и пришли на вход. (Если требуется алгоритм на большом окне, внутри process() можно накапливать данные в кольцевом буфере.) Web Audio примерно:

> const stream = await navigator.mediaDevices.getUserMedia({audio: true});
>
> const audioCtx = new AudioContext({latencyHint: 'interactive', sampleRate: 48000});
>
> const source = audioCtx.createMediaStreamSource(stream);
>
> await audioCtx.audioWorklet.addModule('processor.js'); // содержит класс AudioWorkletProcessor
>
> const procNode = new AudioWorkletNode(audioCtx, 'processor');
>
> source.connect(procNode).connect(audioCtx.destination);

Такая схема минимизирует задержку захвата и обработки. Код processor.js обрабатывает данные в методе process(inputs, outputs). Не выполняем в нём тяжёлые операции, а, при необходимости (например, большой FFT или ML-вычисления), передавать массивы в AudioWorkletNode→MessagePort в WebWorker или использовать WASM-модули.

# Time-stretching (изменение скорости без сдвига тона)

Web Audio не предоставляет простого встроенного метода для изменения темпа без изменения высоты. При установке playbackRate у AudioBufferSourceNode скорость меняется вместе с высотой. Для **time-stretching** применяют DSP-алгоритмы: классические **OLA/WSOLA** (Overlap-Add) или **фазовый вокодер** (Phase Vocoder). Например, библиотека SoundTouchJS реализует алгоритм OLA/WSOLA для изменений скорости/тона. Её можно запустить в AudioWorkletProcessor, передавая аудиоблоки и накапливая выход. Другой подход — сплит-трансляция (гранулярный синтез): разбиение сигнала на короткие перекрывающиеся фреймы, которые накладываются с разным шагом. К сожалению, готовых примеров из стандартных Web Audio нет; приходится либо использовать готовые JS-библиотеки (SoundTouchJS или dsp.js), либо вызывать C/C++-код через WebAssembly внутри AudioWorklet. Важный момент — при применении time-stretching в реальном времени увеличивается вычислительная нагрузка и, возможно, задержка. Если нет жёстких требований к задержке, можно также выполнить time-stretching **офлайн** (через OfflineAudioContext), а потом проигрывать уже скорректированный звук с AudioBufferSourceNode.

# Сравнение aubio.js и Essentia.js

| **Параметр** | **aubio.js** | **Essentia.js** |
|----|----|----|
| **Функции анализа** | Pitch (YIN и другие), Tempo (BPM). Есть простые инструменты для детекции высоты и темпа. Нет из коробки механизмов для детекции всех onsets/ударов. | Огромный набор MIR-алгоритмов (Pitch, Onset, Beat, MFCC, HPCP, спектр. моменты и др.). Включает предобученные ML-модели. |
| **Точность** | Базовые алгоритмы (YIN и пр.) — приемлемая для простых задач. Менее точен на сложных сигналах с шумом/гармониками. | Очень высокая: использует фреймворк Essentia C++, включая современные методы (мелодическая детекция, сверточные сети и т.д.). |
| **Производительность** | Легковесный (несколько сотен КБ), работает быстро на одиночном потоке. Нет WebGPU. Может не справляться с тяжёлой нагрузкой. | Сборка ~2.5МБ (WASM + JS). Оптимизированный C++ в WebAssembly, может использовать WASM SIMD и многопоточность (при изоляции). Вызывает больше загрузку CPU/памяти. |
| **Браузерная поддержка** | Любые современные браузеры с WASM (Chrome, Firefox, Safari, Edge, мобильные). | Аналогично, но для включения многопоточности/SIMD требуется строжайшая изоляция (COOP/COEP). |
| **Лицензия** | MIT (свободная). | AGPLv3 (ограничения на коммерческое использование). |
| **Примеры интеграции** | Простая асинхронная загрузка: aubio().then(({Pitch})=>{/\*...\*/}). | Использование ES6: EssentiaWASM().then((Essentia) => { const e = new Essentia(); ... }); с последующими вызовами методов библиотеки. |
| **Ограничения** | Ограничен набор функций. Требует явной буферизации аудиоданных. Не предоставляет high-level API. | Большой объём кода, долгий первый загруз. Для потоковой работы нужен StreamingWASM- билд или AudioWorklet. |

В итоге aubio.js подходит для простых задач детекции высоты и темпа в браузере без сложной настройки, а Essentia.js — мощный, но тяжёлый инструмент для комплексного анализа аудио с высоким качеством, если не критичен размер и задержка.

# CREPE (точное определение высоты тона)

CREPE — нейросетевая модель (CNN) для монофонической оценки фундаментальной частоты (Pitch) с очень высокой точностью. В браузере её можно запустить через **ONNX Runtime Web** или **TensorFlow.js** (сконвертировав модель). Основные характеристики CREPE:

- **Архитектура и модели:** CREPE обучена на сигнале 16 кГц и использует скользящее окно (по умолчанию шаг 10 мс). Существует несколько вариантов модели (tiny, small, medium, large, full), где full даёт максимальную точность, а tiny — минимальную задержку и размер.

- **Входные данные:** аудиосигнал в 16 000 Гц (иначе требуется ресемплинг). Для real-time обычно буферизуют, например, по 1024 сэмпла (64 мс), переупаковывая с шагом 10–20 мс.

- **Качество и задержка:** CREPE выдаёт тон с точностью до нескольких центов даже на пении/музыке. Задержка складывается из длины окна (~64 мс) и вычислительной задержки нейросети. В браузере на GPU (WebGL/WebGPU) или с SIMD эта задержка минимальна, на CPU дольше.

- **Запуск через ONNX/TensorFlow.js:** для ONNX есть пакет onnxruntime-web, который может использовать бэкенды WASM, WebGL или WebGPU. TensorFlow.js поддерживает загрузку SavedModel через tf.loadGraphModel и бэкенды WebGL (GPU) или WASM. ONNX Runtime Web: при deviceType:'gpu' может использовать WebGL/WebGPU, при deviceType:'cpu' — WASM. TensorFlow.js: можно включить WebAssembly с SIMD, либо WebGL (в т.ч. с WebGPU-беком в новых версиях) для ускорения.

- **Оптимизация:** ONNX-модель можно квантовать или использовать облегчённую версию tiny/medium. TensorFlow.js-версии тоже можно тюнинговать (использовать веса с пониженной точностью). Для ускорения важны SIMD и multithreading (SharedArrayBuffer) — см. ниже.

Таким образом, CREPE позволяет получить очень точную величину частоты в реальном времени. При интеграции: обычно помещают модель в WebWorker или AudioWorklet, подавая на вход аудиоданные из AudioContext. Критерии оценки: сравнить предсказание CREPE с опорными частотами (например, синтетических сигналов) и измерять полную задержку обработки.

# Совместимость браузеров и условия изоляции

- **Web Audio, AudioWorklet, getUserMedia:** Все современные десктоп-браузеры (Chrome, Edge, Firefox, Safari) и мобильные (Chrome/Firefox на Android, Safari на iOS) поддерживают Web Audio API и AudioWorklet. GetUserMedia для аудио поддерживается с ~2017 года во всех браузерах. AudioWorklet введён в Chrome ~66+, Firefox 76+, Safari 14.1+; ScriptProcessorNode считается устаревшим и не должен использоваться.

- **SharedArrayBuffer и WASM-потоки:** Современные браузеры **поддерживают** SharedArrayBuffer и многопоточность WebAssembly **только в случае кросс-оригинальной изоляции** (см. ниже). Поддержка присутствует в Chrome 92+, Edge 92+, Firefox 79+, Safari 15.2+. Без заданных заголовков COOP/COEP конструктор SharedArrayBuffer недоступен. Atomics доступен всегда, но разделяемая память — только при window.crossOriginIsolated == true.

- **WebAssembly SIMD:** Поддерживается в **всеми современными движками**: Chrome/Edge (91+), Firefox (89+), Safari (16.4+) и др. Позволяет ускорить численные вычисления.

- **WebGPU:** На момент 2026 года WebGPU стабильно включён в **Chrome/Edge (113+) и Opera (99+)**. В **Firefox** и **Safari** пока требует флага или находится в стадии тестирования. Если WebGPU недоступен, можно использовать WebGL/WebGL2 с onnxruntime-web или TensorFlow.js.

- **Cross-Origin Isolation (COOP/COEP):** Для таких функций, как SharedArrayBuffer, WebAssembly Threads или WebGPU (в ряде реализаций), требуется включить изоляцию. Для этого сервер должен отдавать заголовки:

> Cross-Origin-Opener-Policy: same-origin
>
> Cross-Origin-Embedder-Policy: require-corp

Либо вместо require-corp можно использовать credentialless (Chrome/Edge, Safari 16+):

> Cross-Origin-Embedder-Policy: credentialless
>
> Cross-Origin-Opener-Policy: same-origin

В таком режиме браузер разрешит загружать ресурсы без учёта третьесторонних cookie. Все внешние ресурсы (скрипты, WASM, аудио и т.д.) должны быть либо с CORS-разрешением, либо иметь заголовок Cross-Origin-Resource-Policy (например, same-origin или cross-origin), иначе загрузка будет заблокирована. Текущее состояние изоляции можно проверить свойством window.crossOriginIsolated (будет true, когда включены все требования). Без изоляции нельзя использовать потоки (SharedArrayBuffer не работает).

# Архитектура и прототипирование

## Архитектура

- Центр — AudioContext с опцией latencyHint:'interactive'. Микрофон подключается через MediaStreamAudioSourceNode, далее — к AudioWorkletNode для обработки (например, FeatureExtractor или PitchDetector). Параллельно может идти AudioBufferSourceNode для аудио из файлов.

- **Потоки:** Тяжёлые вычисления (WASM, ML-модели) выносить в WebWorker/AudioWorklet. Например, CREPE можно выполнить внутри AudioWorkletProcessor или отправлять данные из него в Worker. aubio.js предлагается в виде асинхронного WASM-модуля с поддержкой синхронного импорта для AudioWorklet.

- **Разделение ответственности:** AudioWorklet контролирует I/O и синхронизацию с аудиодорожкой; собственно анализ (aubio, CREPE) может работать в потоке или WebWorker с SharedArrayBuffer для обмена блоками.

## Сравнение поддержки технологий в браузерах (2026)

| **Технология** | **Chrome/Edge** | **Firefox** | **Safari (Desktop/iOS)** | **Замечания** |
|----|----|----|----|----|
| **getUserMedia (audio)** | Да (с Chrome 38+) | Да (с ~21) | Да (с Safari 11+) | Могут потребоваться HTTPS |
| **AudioWorklet** | Да (с 66) | Да (с 76) | Да (с 14.1) | Перебоев нет |
| **AudioBufferSourceNode.playbackRate** (PitchShift) | Да | Да | Да | Меняет тон вместе со скоростью |
| **SharedArrayBuffer/WASM Threads** | Да (с 92, с COOP/COEP) | Да (с 79, с COOP/COEP) | Да (с 15.2, с COOP/COEP) | Требует COOP/COEP |
| **WebAssembly SIMD** | Да (91+) | Да (89+) | Да (16.4+) | Поддерживается в Release |
| **WebGPU** | Да (113+) | Частично (флаг) | Частично (TP) | Chrome/Edge stable |
| **WebAudio Tune (встроенный)** | Нет (нужно DSP) | Нет | Нет | Только сторонние DSP |

## План прототипирования

1.  **Базовый поток:** Написать страницу, которая запрашивает микрофон, создаёт AudioContext({latencyHint:'interactive'}) и соединяет MediaStreamAudioSourceNode → AudioWorkletNode → AudioContext.destination. Измерить базовую задержку (например, по context.baseLatency или таймером).

2.  **Интеграция библиотеки анализа:** Подключить aubio.js и/или Essentia.js. В AudioWorkletProcessor или WebWorker реализовать простой извлекатель признаков — например, оценку высоты тона каждые 10–50 мс. Оценить время выполнения (performance.now()) на различных браузерах. Проверить точность: подать на вход эталонный сигнал (звуковой сигнал с известной частотой) и сравнить результат (рассчитать погрешность в центах или Гц).

3.  **Добавление CREPE:** Загружать модель CREPE через ONNX Runtime Web или tf.js (из AudioWorklet или WebWorker). Использовать небольшой буфер (например, 1024 отсчёта) и вызывать session.run() или model.predict(). Измерять производительность: время запуска модели для одного окна. Сравнить точность и задержку CREPE с классическими методами (YIN и пр.). При необходимости перекалибровать размер окна/шаг (10–20 мс) для баланса.

4.  **Оптимизация:** Если задержка критична, включить Cross-Origin Isolation (добавить заголовки COOP+COEP) и пересобрать WASM-библиотеки с потоками/SIMD. Повторить замеры latency и CPU после включения многопоточности (возможность использовать несколько ядер). Для WebGPU включить соответствующий бэкенд в ONNX (при поддержке) и сравнить скорость.

5.  **Сравнительный анализ:** Собрать результаты: например, таблицу с задержкой (мс) и точностью (среднеквадратичная ошибка частоты) для каждой связки (aubio, essentia, CREPE) на разных браузерах. Выделить, какие методы и настройки дают приемлемый результат.

**Источники:** спецификации Web Audio API, документация веб (ChromeDev, MDN), официальные репозитории aubio.js и Essentia.js, документация CREPE, руководства ONNX Runtime Web и материалы по COOP/COEP.
