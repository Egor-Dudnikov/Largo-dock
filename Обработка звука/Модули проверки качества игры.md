# Общая схема

```text
[Микрофон]
    │
    ▼
[ФРОНТЕНД: real-time проверка]
    ├── [Модуль захвата аудио]
    ├── [Модуль калибровки задержки]
    ├── [Модуль детекции онсетов]
    ├── [Модуль детекции высоты]
    ├── [Модуль сопоставления с эталоном]
    ├── [Модуль скоринга]
    └── [Модуль подсветки и буферизации]
    │
    ▼ (по завершении — события, не аудио)
[БЭКЕНД: детальная проверка, опционально]
    ├── [Модуль приёма отчёта тренировки]
    ├── [Модуль пересчёта отчёта]
    └── [Модуль сохранения и агрегации]
```

**Ключевой принцип:** real-time фидбэк считается **только на фронтенде** — сетевая задержка убивает интерактивность. Бэкенд получает **уже готовые события** (`time_ms`, `note`, `status`, `deviation_ms`), а не аудио, и используется для истории, агрегации и опционального пересчёта.

# Как это делается технически

```text
[Микрофон]
    │ getUserMedia
    ▼
[AudioContext / AudioWorklet]
    │ PCM-блоки по 128–256 сэмплов (~3–6 мс)
    ▼
[Детекция онсетов] (события «удар по струне»)
    │
    ▼
[Детекция высоты] (F0 в окне вокруг онсета)
    │
    ▼
[Сопоставление с эталоном]
    ├── DTW по нотам (или windowed DTW по кадрам)
    ├── сравнение pitch с допуском
    └── сравнение onset с эталонным временем
    │
    ▼
[Скоринг] (JSON-отчёт)
    ├──► [Подсветка нот на AlphaTab] — мгновенно
    └──► [Отправка отчёта на бэкенд] — для истории
```

**Ключевые технологии:**
- **`AudioWorklet`** — обработка аудио в реальном времени в отдельном потоке, без блокировки UI.
- **WebAssembly** — `aubiojs` (порт aubio: YIN, onset, beat) и `essentia.js` (PitchYin, PitchYinFFT, OnsetDetection). Работают быстро, мало весят.
- **TensorFlow.js / ONNX Runtime Web** — CREPE в браузере. Модель `crepe` (npm) или ONNX-экспорт; бэкенды WebGL / WebGPU / WASM.
- **WebGPU** — в 2026 году доступен в Chrome, Edge, Safari 26+, Firefox; ускоряет инференс CREPE на порядок.
- **`SharedArrayBuffer`** — для связки `AudioWorklet` + WASM; требует COOP/COEP-заголовков на сервере.

# Фронтенд-модули

## 1. Модуль захвата аудио

**Краткое описание.** Захватывает звук с микрофона и передаёт PCM-блоки в обработку без блокировки UI.

**Вход.** Разрешение пользователя на микрофон (`getUserMedia`); параметры устройства.

**Что происходит.** Запрашивает доступ к микрофону, создаёт `AudioContext` и `AudioWorklet`. Разбивает аудиопоток на блоки по 128–256 сэмплов (~3–6 мс). Передаёт блоки в модули детекции онсетов и высоты. При необходимости использует `SharedArrayBuffer` для связи с WASM (требует COOP/COEP-заголовков от Go-сервера). Ведёт индикатор уровня громкости для UI.

**Выход.** Поток PCM-блоков; индикатор уровня; флаг готовности записи.

**Технологии.** `getUserMedia`, `AudioContext`, `AudioWorklet`, `SharedArrayBuffer`.

## 2. Модуль калибровки задержки

**Краткое описание.** Измеряет и компенсирует задержку аудиотракта до начала сессии.

**Вход.** Команда калибровки; метроном; запись 4–8 кликов.

**Что происходит.** Включает метроном, пользователь играет клики. Сравнивает записанные онсеты с эталонными кликами, вычисляет среднее отклонение (offset) и запоминает его. Дополнительно читает `AudioContext.baseLatency` и `outputLatency` как приблизительную оценку. Применяет offset ко всем последующим сравнениям. В опытном режиме даёт ручной ползунок «компенсация задержки».

**Выход.** Значение offset в миллисекундах; флаг откалиброванности.

**Технологии.** `AudioContext.baseLatency`, `outputLatency`, кросс-корреляция, `aubiojs` (onset).

## 3. Модуль детекции онсетов

**Краткое описание.** Находит моменты удара по струнам в реальном времени.

**Вход.** PCM-блоки из модуля захвата.

**Что происходит.** Вычисляет спектральный поток (spectral flux) или энергию по блокам. Детектирует пики, соответствующие атакам. Фильтрует ложные срабатывания по порогу и минимальному интервалу. Передаёт события онсетов в модуль сопоставления.

**Выход.** Поток событий `onset` с временными метками.

**Технологии.** `aubiojs` (onset), `essentia.js` (OnsetDetection), spectral flux в `AudioWorklet`.

## 4. Модуль детекции высоты

**Краткое описание.** Определяет основную частоту (F0) в окне вокруг онсета.

**Вход.** PCM-блоки; события онсетов.

**Что происходит.** Для каждого онсета берёт окно 30–60 мс и вычисляет F0 через YIN/pYIN. При наличии ресурсов и WebGPU использует CREPE через ONNX Runtime Web / TF.js. Сравнивает F0 с эталонной частотой ноты с допуском (например, ±30 центов). Возвращает высоту и уверенность.

**Выход.** Событие `note_detected` с F0, ближайшей нотой и уверенностью.

**Технологии.** `aubiojs` (YIN), `essentia.js` (PitchYin, PitchYinFFT), CREPE через ONNX Runtime Web / TF.js (WebGPU → WASM fallback).

## 5. Модуль сопоставления с эталоном

**Краткое описание.** Сопоставляет события пользователя с эталонными нотами по времени.

**Вход.** События `onset` и `note_detected`; эталонный MIDI/табулатура; offset из калибровки.

**Что происходит.** Выполняет DTW на уровне нот: строит матрицу между последовательностью эталонных нот и событиями пользователя. Учитывает offset калибровки. Для каждой эталонной ноты находит ближайшее событие пользователя. Фиксирует пары «эталон — исполнение» с отклонением по времени и высоте.

**Выход.** Список пар `note_match` с полями `expected`, `played`, `time_deviation_ms`, `pitch_deviation_cents`.

**Технологии.** Чистый JS; DTW на уровне нот (матрица ~300×300); windowed DTW для длинных треков.

## 6. Модуль скоринга

**Краткое описание.** Формирует отчёт по каждой ноте и общую оценку.

**Вход.** Список `note_match`.

**Что происходит.** Классифицирует каждую пару: `correct`, `wrong_pitch`, `missed`, `bad_timing`. Считает точность, среднее отклонение по времени и высоте. Формирует JSON-отчёт в том же формате, что и бэкенд.

**Выход.** JSON-отчёт: массив `note_results` и агрегаты.

**Технологии.** Чистая арифметика на JS.

## 7. Модуль подсветки и буферизации

**Краткое описание.** Мгновенно окрашивает ноты на AlphaTab и накапливает события для отправки.

**Вход.** JSON-отчёт; буфер событий.

**Что происходит.** Применяет цвета к нотам: correct, wrong, missed, bad_timing. Обновляет UI без перерисовки всего стана. Накапливает события в буфер. По завершении сессии отправляет только события (`time_ms`, `note`, `status`, `deviation_ms`) на бэкенд.

**Выход.** Подсветка на табах; JSON-буфер для отправки.

**Технологии.** AlphaTab API; `fetch`/WebSocket для отправки событий.

# Бэкенд-модули

## 1. Модуль приёма отчёта тренировки (Go)

**Краткое описание.** Принимает события от фронтенда и сохраняет их.

**Вход.** JSON-отчёт от фронтенда: `note_results`, агрегаты, `session_id`.

**Что происходит.** Валидирует структуру отчёта, привязывает к `training_session` и эталонной табулатуре. Сохраняет `note_results` и `problem_segments` в БД. Обновляет статус сессии.

**Выход.** Запись в БД; статус `received`.

**Технологии.** Go: `net/http`, JSON-валидация; PostgreSQL.

## 2. Модуль пересчёта отчёта (опциональный «точный режим», Python)

**Краткое описание.** Пересчитывает отчёт по полному контексту более тяжёлой моделью.

**Вход.** События фронтенда; опционально аудиозапись (если пользователь согласился отправить).

**Что происходит.** Запускается только по запросу или для слабых устройств. Выполняет CREPE full на аудио (если есть), DTW по кадрам, более точную классификацию отклонений. Формирует уточнённый отчёт. Сравнивает с отчётом фронтенда для калибровки порогов.

**Выход.** Уточнённый JSON-отчёт; метрики расхождения с фронтендом.

**Технологии.** Python: CREPE, pYIN, DTW; опционально GPU.

### 3. Модуль сохранения и агрегации (Go)

**Краткое описание.** Хранит историю и агрегирует статистику по пользователю и треку.

**Вход.** Отчёты (фронтенда и/или пересчитанные).

**Что происходит.** Сохраняет результаты сессий. Считает общую точность, график ритма, проблемные такты. Формирует данные для дашборда. Отдаёт историю по запросу.

**Выход.** Агрегаты для дашборда; история тренировок.

**Технологии.** Go: SQL-агрегация; PostgreSQL.
